# 金魚審（零上文審查）— {{REPO_NAME}}

> **幾時用**：寫完一份要**另一個人／另一個 AGENT 自己執行**嘅文件（README、SCOPE、派工指令、ADR、runbook），交付前搵一對「零上文」嘅眼睇一次。
> **規則來源**：真理倉 [docs/52](https://github.com/playerkousas-rgb/readme/blob/main/docs/52-fresh-eyes-review.md)（方法借 `google/elephant-goldfish-model`，Apache-2.0，**冇安裝**）。本頁只係貼用嘅執行版，唔重抄理由。

## 一條紅線

**審你份文件嘅人，唔可以係寫嗰個人，亦唔可以睇過你點解咁寫。**

呢個 repo 冇 subagent tool → 「金魚」＝**開一個新對話**。
喺同一個對話自己審自己、或者叫同一個模型「用零上文角度再睇」，**唔算**。冇做就照寫「未做金魚審」。

## 喺 Arena 開新對話 ＝ 隔離更徹底

新對話嘅 AGENT **連底層模型都可能唔同**（Arena 用多個模型）→ 唔止換 context，連「同一個模型嘅盲點」都換走。比上游 EGM 金魚更徹底。

代價同對策：

| 風險 | 對策 |
|---|---|
| 冇檔案系統，開唔到 repo | **連全文貼** |
| 唔知本倉慣例（語言／格式／`docs/NN`） | 委託書寫死「唔准建議改語言／風格」 |
| 會用另一套審美 | 只收「讀唔明乜」，**唔收「應該點寫」** |

## 點做（三步）

1. 開一個**新對話**（唔要帶任何上文）。
2. 貼下面 §段落 ＋ 文件全文（或路徑／URL）。
3. 收貨：先讀 reviewer 嘅**兩段改寫**，睇下係唔係等於你原意。**唔等於 → 問題喺文件，唔喺 reviewer。**

## 貼用段落

```text
你係第一次接觸呢個 project 嘅讀者。你唔知任何背景，我亦唔會補充。
只讀下面呢份文件，然後照次序做：

1) 先用你自己嘅話寫兩段：① 呢份文件主張做乜 ② 按佢所講，現有系統點運作。（每段 2–5 句）
2) 逐個列出你唔明嘅地方。每個寫：嚴重程度（CRITICAL／HIGH／MEDIUM／LOW）、位置（章節標題或行號）、你缺咩上文。最多 50 條，超出寫「其餘 N 條同類」。
3) 只捉「呢個 project 特有而又冇解釋」嘅名詞；通用工程名詞（API、cache、idempotent）唔使捉。
4) 唔准讚、唔准講「整體清晰」。冇發現就照講冇發現。
5) 唔准建議改法（唔好講「應該改成…」）——只講你缺咩、邊句讀唔明。
6) 唔准建議改語言／翻譯／語氣：本倉刻意用固定語言同格式，唔係錯。
7) 唔准改任何檔案。開唔到路徑就照講「我開唔到」，唔好靠估。

文件：<貼全文，或貼路徑／URL>
```

## 收貨 checklist

- [ ] reviewer 有寫兩段改寫，而你讀完覺得「就係呢個意思」
- [ ] 每個 finding 有嚴重程度 ＋ 位置（章節或行號）
- [ ] 係**新對話**做（唔係自己審自己）
- [ ] 同一份文件最多重審 **1** 次；剩餘爭議寫低做「接受風險」，唔好無限改標點
- [ ] 真係有人讀錯 → 改**文件**，唔好改 reviewer
