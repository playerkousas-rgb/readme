# 金魚審委託書（填檔名即可貼去新對話）

> **用法**：① 揀一份文件 → ② 把 `<檔名>` 兩處填好 → ③ **開一個新對話** → ④ 連文件全文一齊貼。
> **唔好**喺原本嗰個對話貼（咁樣唔算金魚審，見真理倉 [docs/52 §0](https://github.com/playerkousas-rgb/readme/blob/main/docs/52-fresh-eyes-review.md)）。
> **唔好**加任何背景、唔好講你之前改過乜、唔好講你想佢讚。

## 貼用段落（由下面第一行 copy 到最尾）

```text
你係第一次接觸呢個 project 嘅讀者。你唔知任何背景，我亦唔會補充。

只讀下面呢份文件（<檔名>），然後照次序做：

1) 先用你自己嘅話寫兩段：
   ① 呢份文件主張做乜
   ② 按佢所講，現有系統點運作
   （每段 2–5 句）

2) 逐個列出你唔明嘅地方。每個寫齊三樣：
   - 嚴重程度：CRITICAL／HIGH／MEDIUM／LOW
     CRITICAL＝照住做會出事（刪資料、違反上面明講嘅定案、或整份讀唔明）
     HIGH＝兩處講法相反、或冇寫驗收方法（做完唔知算唔算做完）
     MEDIUM＝冇交代邊界／例外／回復方法，但唔會即刻錯
     LOW＝用字、格式、重複
   - 位置：章節標題或行號
   - 你缺咩上文（一句講清）
   最多講 50 條；超出就寫「其餘 N 條同類」。

3) 只捉「呢個 project 特有而又冇解釋」嘅名詞（例如指令名、欄位名、檔名）。
   通用工程名詞（API、cache、idempotent、localStorage）唔使捉。

4) 唔准讚、唔准講「整體清晰」。冇發現就照講冇發現。

5) 唔准建議改法（唔好講「應該改成…」）—— 只講你缺咩、邊句讀唔明。

6) 唔准建議改語言／翻譯／語氣。本倉刻意用廣東話書面語同固定格式
   （EXCEPTION: 格式、docs/NN 命名），呢啲唔係錯。

7) 唔准改任何檔案。開唔到路徑就照講「我開唔到」，唔好靠估。
   下面已經貼咗全文，唔需要開檔案。

文件全文如下：
──────── 由下一行開始 ────────
<貼全文>
──────── 貼到呢行為止 ────────
```

## 收貨（作者自己做）

| 步 | 做乜 |
|:--:|---|
| 1 | 先讀 reviewer 第 ① 段改寫，問自己：**呢個係唔係我原意？** |
| 2 | 唔係 → **問題喺文件，唔喺 reviewer**。改文件，唔好同 reviewer 辯 |
| 3 | 逐條 finding 分類：真缺上文／風格偏好（丟）／佢誤解（可能係文件寫得衰） |
| 4 | **「應該改英文／改正式啲／換架構」一律丟** —— 佢唔知本倉慣例 |
| 5 | 修完最多**重審 1 次**；仍然有 CRITICAL → **改結構**，唔好再審 |
| 6 | 剩餘爭議寫落「接受風險」，唔好無聲消失 |
