# 52 — 金魚審（零上文審查）：改寫先行，捉「零件齊但駁唔埋」

> **2026-11-19 落地**。來源：[`google/elephant-goldfish-model`](https://github.com/google/elephant-goldfish-model)（Apache-2.0，v0.1.1，commit [`70406c4`](https://github.com/google/elephant-goldfish-model/tree/70406c4d22cc7ea8299637c2c5b44625c48b3f08)）—— **只讀方法，冇 clone、冇安裝、冇裝 plugin、冇加任何 dependency**。
> **適用**：真理倉嘅新規則、新 `docs/` 章節、要貼去其他 repo 嘅派工指令、大改一份已有文件。
> **唔新增規則 ID**（同 [47](47-readme-discipline.md) 一樣，本頁只講「幾時用同點用」）；對應 [F16](../PLAYBOOK.md) 四處同步同 [47 原則二](47-readme-discipline.md)（「已修」要寫得出驗證方法）。

## 0. 一句判決同誠實限制

一句：**審你份文件嘅人，唔可以係寫嗰個人，亦唔可以睇過你點解咁寫。**

| 項目 | 實情 |
|---|---|
| 上游做乜 | 大象（有全部上文）寫設計文件 → **金魚**（全新 context、零對話紀錄、只讀檔）分階段挑漏 |
| 我哋有冇 subagent | **冇**——呢個 repo 冇 Skill tool／plugin harness（見 [CATALOG 未核實](../templates/repo-starter/skills/CATALOG.md)） |
| 所以「金魚」＝ | **開一個新對話**，只貼檔案或全文 ＋ 下面 §4 嗰段；唔貼背景、唔講你之前改過乜、唔講你想佢讚 |
| 上游自己都咁講 | 原文意思：冇 subagent tool 就**停手同用戶講**——同一個 context 做嘅 review **唔算**金魚 review |

> **唔准扮做到**：喺同一個對話「自己審自己」、或者叫同一個模型「用金魚角度再睇一次」，都唔算。
> 冇開新對話就照實寫「未做金魚審」（[47 原則三](47-readme-discipline.md)：未做要老實列）。

### 0.1 喺 Arena 做，隔離比上游更徹底（2026-11-19 用戶指出）

| 項目 | 上游 EGM 金魚 | **我哋（Arena 開新對話）** |
|---|---|---|
| 換咗乜 | 只換 **context**（新 session，同一個 harness、同一個模型族） | 換 **context ＋ 可能換埋底層模型**（Arena 用多個模型） |
| 佢識唔識你 | 唔識你之前嘅對話 | **唔識你、亦唔識上一個 AGENT 嘅答案**——連「慣性口味」都冇 |
| 隔離強度 | 好 | **更強**（唔會延續同一個模型嘅盲點） |

**但代價有三個，必須喺委託書寫明**（見 §4）：

| 風險 | 點解 | 對策 |
|---|---|---|
| **冇檔案系統** | 新對話嘅 AGENT 未必開得到呢個 repo | **連全文貼**，唔好只講路徑 |
| **唔知本倉慣例** | 唔知我哋用**廣東話書面語**、`EXCEPTION:` 格式、`docs/NN` 命名 | 委託書寫死「唔准建議改語言／風格」 |
| **會用另一套審美** | 另一個模型可能覺得廣東話「唔專業」而建議改英文 | 同上：**只講「你讀唔明乜」，唔講「應該點寫」** |

### 0.2 一個對話審幾多份？（2026-11-19 用戶裁決）

用戶原話：「Arena 每次開嘅連底層都唔同，還不是新 AGENT？」——**係，所以判準係「對話」，唔係「檔案」**：

| 情況 | 算唔算金魚 | 點解 |
|---|---|---|
| 新對話審**第 1 份**文件 | **算** | 零上文、唔識作者、可能唔同模型 |
| **同一個新對話**審**第 2、3 份**文件 | **算**（`docs/55` 就係呢種） | 作者仍然唔在場；我之前只讀過我**自己**審嘅嘢，冇讀過「你點解咁寫」。**唯一代價**：唔算「重審獨立」，之前讀過嘅檔要另有可 grep 證據 |
| **同一份文件**再審第 2 次 | 算「**重審**」，受 §2 一次上限規管 | 第 1 次嘅 findings 已經污染咗我 |
| 同一個對話、作者喺場（即 docs/53） | **唔算**（§0） | 審嘅人自己就係寫嗰個人 |

> 一句：**「新對話」隔離嘅係「作者上文」；「換檔案」唔會重新隔離。** 所以另一個 AGENT 唔需要扮「模擬」——照寫金魚，但老實講「我之前讀過邊幾份」。

## 1. 三個審查向量（抄方法，唔抄 code）

### 1.1 改寫先行（最值錢嘅一條）

reviewer 第一步**唔准列問題**，要先用自己嘅話寫兩段：

1. **呢份文件主張做乜**（2–5 句）
2. **按呢份文件所講，現有系統點運作**（2–5 句）

然後作者對照自己原意。**改寫錯咗，本身就係一個 finding。**

點解有效（上游原文意思）：淨係列「未定義名詞」，捉唔到一種文件——**每個名詞都定義咗，但各部分駁唔埋**。改寫捉得到。

> 我哋最常撞嘅正正係呢種：兩份文件各自寫得通順、每個名詞都解釋過，但兩份放埋一齊就矛盾（例如同一份文件前面寫「X 可以放行」、後面寫「X 永遠剔除」）。結構檢查同 stale 指紋都捉唔到，因為兩句自己都冇錯。

### 1.2 未定義／未連檔嘅概念

只捉**本專案特有**而又冇解釋嘅名詞：`portalIds`／`silentPortalIds`／`supportNudge`／`entry-gate`／`Delist → Gate → Soft → Hard` 四個下架齒輪。

**唔准捉**通用工程名詞（API、cache、idempotent、localStorage）。上游原句大意：你唔識**呢個 project**，但你識軟件。

### 1.3 假設咗嘅前提

講「點做」但當讀者已經知前置步驟。典型三種：

- 叫跑 `preflight`，但冇講要由真理倉抄邊幾支 script；
- 叫「加白名單」，但冇講 `<slug>` 要對 seed 核實（SG18）；
- 叫「改一行」，但冇講行號會漂。

## 2. 三條紀律

| 紀律 | 內容 | 點解 |
|---|---|---|
| **reviewer 只讀** | 唔准改檔、唔准「順手幫你修」 | 一改就變咗作者，之後捉唔到自己嘅錯 |
| **一次 re-audit cap** | 同一份文件最多重審 **1** 次；之後剩低嘅寫入「接受風險」，唔好無限 loop | 防止最後變成改標點 |
| **報告落地成檔** | 唔准喺對話倒長篇；寫落檔再講路徑 | 作者可以逐條剔、逐條覆，唔會淹沒喺對話 |

### 2.1 一貼即用嘅委託書

唔想自己砌：用 [`templates/repo-starter/FRESH-EYES-REQUEST.md`](../templates/repo-starter/FRESH-EYES-REQUEST.md) —— 填入檔名，連全文貼去新對話即可。入面已經包含 §4 嘅規矩、建議審查次序同收貨記錄格式。

## 4. 貼去新對話嘅固定段落

```text
你係第一次接觸呢個 project 嘅讀者。你唔知任何背景，我亦唔會補充。
只讀下面呢份文件，然後照次序做：

1) 先用你自己嘅話寫兩段：① 呢份文件主張做乜 ② 按佢所講，現有系統點運作。（每段 2–5 句）
2) 逐個列出你唔明嘅地方。每個寫：嚴重程度（CRITICAL／HIGH／MEDIUM／LOW，定義見下面）、位置（章節標題或行號）、你缺咩上文。
3) 只捉「呢個 project 特有而又冇解釋」嘅名詞；通用工程名詞（API、cache、idempotent）唔使捉。
4) 唔准讚、唔准講「整體清晰」。冇發現就照講冇發現。
5) 唔准建議改法（唔好講「應該改成…」）——只講你缺咩、邊句讀唔明。
6) 唔准建議改語言／翻譯／語氣：本倉用**廣東話書面語**同固定格式（`EXCEPTION:`／`docs/NN`），呢啲係刻意嘅，唔係錯。
7) 唔准改任何檔案。開唔到路徑就照講「我開唔到」，唔好靠估。

文件：<貼全文，或者貼路徑（開唔到就要作者補貼全文）>
```

**收貨重點**：作者先讀第 ① 段改寫，睇下係咪等於自己原意。
**唔等於 → 問題喺文件，唔係喺 reviewer。**

**用另一個模型審嗰陣，多一重過濾**：reviewer 講「應該改英文／改正式啲／改用另一個架構」一律**當噪音**——
佢唔知本倉慣例，呢啲屬「風格偏好」而唔係「讀唔明」。只收「我缺咩上文」「邊句前後打架」。

### 嚴重程度四級（借 GitHub Spec Kit `/analyze`）

| 級 | 定義 | 例子 |
|---|---|---|
| **CRITICAL** | 照住做會出事：刪資料、違反用戶明確定案、或整份文件讀唔明 | 叫用家清 localStorage 但冇提匯出備份 |
| **HIGH** | 兩處講法相反、或冇寫驗收方法（做完唔知算唔算做完） | 同一文件前段寫「放行」後段寫「剔除」 |
| **MEDIUM** | 冇交代邊界／例外／回復方法，但唔會即刻錯 | 冇寫「掃唔清就問，唔准假設冇」 |
| **LOW** | 用字、格式、重複 | 同一個名詞兩個叫法 |

**上限 50 條**：超出就寫「其餘 N 條同類，唔逐條列」。冇上限嘅 review 會變成第二份文件，冇人睇。

**一次重審就夠**（§2 紀律）：重審完**仍然有 CRITICAL** → 唔好再審，**改結構**（通常係兩條規則互相矛盾，唔係用字問題）。
